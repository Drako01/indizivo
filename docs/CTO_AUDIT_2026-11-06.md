## Hallazgos priorizados: evidencia vs hipotesis

### H-01 — P0 Precision semver: logicamente incorrecta en rangos no detallados en tests (confirmacion mediante prueba pendiente)

Archivo: `src/typed/versions.ts`, funcion `evaluateVersion`, rama `case '~'`.
La implementacion exige mismo major y minor tambien cuando precision del requisito es 1: con el requisito npm `~1`, semver deberia admitir versions `1.x`, mientras el codigo aceptaria solamente `1.0.x`. Otros casos OR y prerelease no estan implementados, si bien algunos devuelven INCONCLUSIVE. Riesgo: error de compatibilidad falso. Reproduccion con test focalizado y comparacion de referencia obligatoria antes de parche.

### H-02 — P0 Inconsistencia target HTTP IPv6 (evidencia de codigo, requiere reproduccion real)

`validateService` acepta `http://[::1]:PUERTO`; `inspectService` pasa callback `lookup: ... 127.0.0.1` para todos los hosts. El destino efectivo podria no corresponder al endpoint aprobado y producir resultado erroneo. Agregar tests reales IPv4/IPv6 y preservacion de target; no ampliar a red no local.

### H-03 — P0/P1 Doc drift verificable

El `package.json` y release GitHub indican 0.1.3, mientras `README.md`, `PRIVACY.md`, `ROADMAP.md` y varios documentos `docs/` se expresan como si 0.1.0 siguiera pendiente, workflows estuvieran apagados o reglas del repo fueran inexistentes. Riesgo: nuevos agentes y contributors aplican estado incorrecto. Crear una sola fuente de verdad actual, mantener historico separado y enlazar SHA/Actions.

### H-04 — P1 Heuristicas mostradas como ports declarados

`discover` agrega puerto 3000 para Next y 5173 para Vite si no detecta puertos explicitos. Son defaults plausibles, no prueba del puerto de esta app. El output siempre advierte que escuchar no prueba conflicto, lo cual es positivo, pero debe etiquetar fuentes observadas vs heuristicas.

### H-05 — P1 Comparaciones de endpoints sin identidad persistente

`verifyServices` usa `service-i` (indice de arreglo) mientras `compareSessions` usa check id como identidad. Tras reordenamientos de targets puede mapear estados de servicios diferentes. Test de reorder/edit de plan para reproducir; proponer UUID/target hash estable por host+endpoint con migracion de history.

### H-06 — P1 Distincion de archivo ausente vs ilegible

`readBounded` devuelve `''` para falta de archivo, symlink, permiso, exceso de bytes y otros errores. `discover` convierte texto vacio en `hasEnvFile:false` u omite check. Riesgo de omision o evidencia incompleta. Usar estados typed Present/Missing/Unreadable/Blocked sin exponer contenido sensible.

### H-07 — P1 Mantenibilidad y aislamiento incompleto

`src/typed/extension.ts` concentra estado, webview bridge, consent, session, storage, reportes, comandos y workflow; `src/typed/ui.ts` mezcla template, CSS, logic de interaccion y traducciones por selectores. Refactor gradual por responsabilidades, sin frameworks nuevos sin ROI. Una reescritura total seria desproporcionada al tamaño del proyecto.

### H-08 — P1 Test E2E insuficiente para UX certificada

`test/vsix-e2e/suite/index.js` y `test/e2e/suite/index.js` hacen afirmaciones sobre el controller dentro del Extension Host, no una suite de clicks, teclado real, screenreader, zoom y topologias remotas completas. El JS de Webview se ejecuta en VM de pruebas, valioso pero no sustitutivo del browser real.

### H-09 — P1 Poca superficie de diagnostico

Soportado hoy: Node/Go versions, claves .env, ports, owner opcional, servicio loopback HTTP aprobado. Se requiere priorizar experiencias reales: monorepos, multiple runtimes, toolchains, Docker/Compose, debugging de bind interfaces y estados de servicios dependientes. No introducir todos simultaneamente.

### H-10 — P2 CI y reporting de estado

`verify.yml` corre tests por PR y push main; `publish.yml` vuelve a correr quality matrix y Linux E2E al aumentar la version. Algunas repeticiones son redundantes si existe evidencia del SHA exacto; otras son requeridas porque el commit de merge cambia el SHA. Implementar politica de reuse por provenance, no quitar checks indiscriminadamente. `open-vsx-publish.mjs` deliberadamente reporta WARN cuando una version no esta activa aunque el job complete success: debe reflejarse como release parcial en estado agregado.

### H-11 — P1 Semantica remote y procesos

`extensionKind:["workspace"]` desplaza la extension al Extension Host remoto cuando corresponda, de acuerdo con VS Code; sin embargo comparacion y texto de puertos no identifican explicitamente namespaces y tests reales WSL/SSH/Containers estan pendientes. No inferir procesos del host local desde un namespace remoto.

### H-12 — P1 Metricas de efectividad inexistentes

Un benchmark sintetico `scripts/benchmark.cjs` mide una carpeta minima con version y puerto; no mide latencia/false positives en proyectos grandes/mixtos, p95 del usuario ni validacion externa. Meta de valor: reproducir un problema real y producir un next action verificable, no simplemente retornar PASS.

## Prioridad recomendada por costo/impacto

1. Corregir veracidad (H-01...H-06) y ordenar estado documental: menor coste, maximo valor en confianza.
2. Seguridad/remote/cancel/process snapshot (H-07/H-11), manteniendo el core local-first y bounded.
3. Introducir un conjunto pequeño de nuevos diagnosticos de alto ROI a partir de escenarios reales y feedback de developers; distinguir observado vs inferido.
4. UX y a11y validada de verdad, comparaciones historicas robustas, EN/ES completo.
5. Engineering/release hardening y rendimiento sobre proyectos reales, sin introducir burocracia ni CI duplicado.

## No afirmaciones sin evidencia

- CI verde en 3 SO NO equivale a flujos visuales E2E en los 3.
- Publication job PASS NO equivale necesariamente a indexacion confirmada y simultanea en los dos markets, salvo evidencia de consulta por registry.
- El benchmark sintetico NO acredita una mejora de tiempos en proyectos reales.
- No se ha establecido un pentest ni un estudio de usabilidad externo.
- "Enterprise AAAA" es un objetivo interno: no es una certificacion oficial de Microsoft.

## Criterios de GO sugeridos

Primero: cero bug P0 de exactitud/consent, matriz de tests de escenarios etiquetados, historial fiable, support matrix respaldada por E2E reales, no secretos exportados, confirmacion de reader/teclado, SLO medidos y estudio con 10-15 developers. Luego, release con aprobacion del owner. Hasta entonces, NO-GO para proclamar AAAA.
